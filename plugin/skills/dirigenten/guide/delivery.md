# Guide: delivery
Subject kind `delivery`. Call `act{on:{kind:"delivery",id}, action, rev, params?}`; the action must be in the envelope's `available`. States: open, closed.

Steps
1. `read{on:{kind:"delivery",id}}` and note `rev` and `available`.
2. Choose the primary action first, or the one that matches what the user asked.
3. Send `act` with that `rev`. If `written` is false, read again (the `rev` moved or the state changed) and decide again.
4. For ◐ ask once per task and day; for ■ call with the same on/action first, show the preview, and send `preview_id` and `user_approval` with the user's exact words, alone.
Missing facts do not stop a draft: write it with (?) where a fact is missing, save it with `act` action `run` and `params.text`, show it to the user and ask for a yes or corrections. Never show ids (t-2) or revisions (rev 1) to the user. Invent no facts: anything not given is (?). Events, visits, dates, prices and what the customer said come from a source: what the user said, the customer's mail or thread, the task's material or what dirigenten holds. Where there is no source, write (?) so the user fills it in. Never remove a (?) without the fact from a source, not even to get past the block on a send; ask for it in your single question about what is missing instead. When you fill a gap, save the text with `params.sources`, one row per gap with `value` and either `quote` (the user's words, verbatim, holding the value) or `ref` (the mail, material or node holding it); a gap dropped without a value is a row with `from: removed`, `reason: tas bort` and her words agreeing to drop it as `user_approval` on the same call (asked in your single question about what is missing); an outward send is shown only with its recipient list saved on it (`write_self` with `params.recipients`), so ask for recipients in that same question; without it no preview of what goes out is shown. A moment a person does, such as reviewing the tone, is marked done only with the user's own words as `user_approval`; never write yourself that it is done. Never send `user_approval` before the user has said yes to the very preview you showed. A claim that something happened, such as a visit, a call, a meeting or that the customer said something, is written only when a source says so; a polite phrase like «Tack för att vi fick titta på ert tak» is such a claim too. Before showing the preview, read your text sentence by sentence against the sources and replace every claim without a source with (?). Once the facts come, save the corrected text and show it in the same question as the preview, so one yes covers both. Do not mark the text done first: ask for the send's preview directly (`act` action `yes` on the send); it shows word for word everything that goes out, texts, images and recipients, and a yes on it marks those moments done too; a moment whose result is not shown in the preview needs its own yes; when another moment comes before the send, such as an image, a recipient list or another text, save its result too (a text with `act` action `run` and `params.text`, a file with `attach_file`) before asking for the preview, and if what you need is missing, such as the image, ask for it in the same question as the other missing facts; at most two questions in all, and the first one always shows the draft. A text changed after a yes needs a new yes before the moment is marked done.
A (?) stops only the send itself, what goes out to the customer. Anywhere else it is kept as an open question when the moment is marked done: say whom it concerns in `params.question_for` (else the customer); Ångra takes it away again. A moment that waits on another is still marked done outside (`done_outside`, ◐) with `reason` and `evidence`.
An unknown field in `params` (one the action does not list below) is refused before anything is written: `missing` names it and gives a template with the action's fields; nothing is dropped silently.
5. Tell the user what happened from `say`. To take it back: `act` with action `undo` takes back the last action (or send the action named as `inverse`).

Actions
- `close` — Stäng leveransen. Means: Leveransen är klar och stängs. Not for: Inte för leveranser som har uppdrag kvar. Severity: ● do directly. Inverse: reopen. From: open.
- `reopen` — Öppna leveransen igen. Means: Leveransen behöver arbetas vidare på. Not for: Inte för att ändra något i den som är levererad. Severity: ● do directly. Inverse: close. From: closed.
- `add_task` — Lägg till en uppgift. Means: En ny uppgift läggs till i leveransen, som en beställning: avtalet och kvoten räknas, och du ser dem före ja:et. Not for: Inte för ett delmål i en uppgift; det är Lägg till ett delmål. Severity: ◐ one yes per task and day. Inverse: none by design. From: open.
- `move_delivery` — Flytta leveransen. Means: Alla uppdragens löften i leveransen flyttas lika många dagar. Du ser varje uppdrags datum före och efter ja:et. Not for: Inte för ett enda moment; flytta det i Tid. Severity: ◐ one yes per task and day. Inverse: move_delivery. From: open.
- `change_responsible` — Byt ansvarig. Means: Den du väljer blir ansvarig för allt som inte är gjort i leveransens uppdrag. Exempel: «Låt Kim ta leveransen.» Not for: Inte för ett enda moment; det är Byt vem. Params: party. Severity: ● do directly. Inverse: change_responsible. From: open.

Example 1: `act{on:{kind:"delivery",id:"<id>"}, action:"close", rev:"<rev>"}` — Stäng leveransen: Leveransen är klar och stängs.
Example 2: `act{on:{kind:"delivery",id:"<id>"}, action:"close", rev:"<rev>"}` (Stäng leveransen, inverse `reopen`) followed by `act{…, action:"undo", rev:"<new rev>"}` when the user changes their mind.
Counterexample: `close` while the delivery is "closed" is refused (Går inte nu: leveransen är stängd. Det som går nu: Öppna leveransen igen.). Do not retry it; read and take what `available` offers.
Edge case: two people act on the same `rev`: one is written, the other gets `written:false` with the new `rev`. Read, then decide again. The `unavailable` list gives `why` and what unlocks it.
